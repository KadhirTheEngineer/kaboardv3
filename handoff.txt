# Kaboard — Hardware Design Handoff

## Project goal

Design a custom, high-performance, wireless, split Hall-effect keyboard in KiCad 10. The intended board has 36 keys total, 18 per half, using low-profile Gateron magnetic switches.

The design philosophy is to integrate proven circuits and existing reference designs rather than inventing unverified electronics. Every component, pin assignment, footprint, and electrical assumption must be checked against official datasheets and reference designs before the schematic is considered final.

The immediate task is to finish the hardware schematic and pin assignments. Do not begin PCB routing or invent missing design decisions.

## 1. Overall architecture

Each keyboard half is completely independent.

* 18 Hall-effect keys per half.
* Each half has its own battery, charger, STM32, nRF52840 radio module, and USB-C charging port.
* No electrical connection between halves.
* No inter-half cable, power sharing, or wired communication.
* Each half communicates wirelessly with a receiver/dongle.
* The receiver presents the keyboard to the host through USB HID.
* Exact RF protocol, receiver architecture, and synchronization between halves are not yet finalized.

Each half contains two MCUs:

**STM32G431RBT6**

* Hall ADC acquisition.
* Sensor calibration and filtering.
* Key position calculation.
* Actuation and rapid-trigger logic.
* Produces the latest processed key-state snapshot.

**nRF52840 module**

* Wireless communication.
* RF scheduling and protocol.
* Communication with the receiver.
* Receives processed key states from the STM32.
* Battery/status reporting and wireless management.

Do not move Hall processing to the nRF or assume the nRF needs all 18 raw ADC values for normal operation.

## 2. USB-C — frozen architecture

USB-C on each half is for power and charging only.

* No wired keyboard HID.
* No USB D+/D− connection to either MCU.
* No USB-PD controller.
* No inter-half connection.
* Standard 5 V USB-C sink.
* Independent 5.1 kΩ Rd resistors on CC1 and CC2.
* USB input protection and ESD must be implemented appropriately.

The keyboard must be able to operate while plugged in and charging. Unplugging USB must transition to battery operation without requiring firmware intervention.

Firmware programming/debugging is through SWD, not USB.

## 3. Hall sensing — architecture selected, exact part still requires final validation

Previous sensor: DRV5056A3. This was abandoned because its active current is unattractive for a battery-powered keyboard.

Current primary candidate: **TI TMAG5253BA3**, analog Hall sensor with an enable/shutdown pin.

The intended sensing architecture is:

```text
18 magnetic switches
        ↓
18 TMAG5253 sensors
        ↓
18 independent analog outputs
        ↓
STM32 ADC1 / ADC2
        ↓
DMA / key processing
        ↓
SPI to nRF52840
```

We considered a 2×9 enable-multiplexed arrangement but decided against it for the high-performance active scan path.

**Selected direction:**

* One independent ADC connection per Hall sensor.
* No external analog mux.
* No shared analog output lines during active operation.
* All 18 sensors continuously enabled during active scanning.
* Common or otherwise deliberate Hall enable control for low-power modes.
* Target high scan performance, potentially 8 kHz, subject to actual timing validation.

Important: “Direct ADC” does not mean all 18 channels convert simultaneously. The STM32 ADCs still sequence or otherwise schedule conversions. The goal is to avoid sensor-bank wakeup/multiplexing delays and simplify the acquisition path.

The TMAG5253BA3 sensitivity variant is a strong candidate based on TI’s keyboard application material, but the exact variant must be checked against the actual Gateron switch magnet and sensor geometry. Do not claim saturation, travel resolution, or magnet polarity has been validated on our switch.

The exact Hall footprint and mechanical placement must come from official package data and a proven compatible HE keyboard implementation. Do not invent the sensor-to-magnet geometry.

No custom sensor test PCB is desired. If validation is needed, prefer existing TI evaluation/adapter hardware and an STM32 development board.

## 4. Battery and power — selected architecture

Each half uses a **1S, approximately 2000 mAh LiPo**. A slim pouch form factor is preferred.

Selected power architecture:

```text
USB-C 5 V
    ↓
USB input protection
    ↓
BQ25185 charger / power path
    ├── 1S protected LiPo
    ↓
SYS_RAW
    ↓
TPS63031 3.3 V buck-boost
    ↓
3V3_SYS
    ├── STM32
    ├── nRF52840
    └── Hall sensors
```

The charger must support simultaneous system operation and battery charging. The regulator must maintain 3.3 V across the useful single-cell battery voltage range.

## 6. nRF52840 module

Selected direction: **Raytac MDBT50Q-family nRF52840 module**.

The exact module suffix/orderable part is not yet frozen. Verify the specific module pinout and electrical requirements before selecting it.

The module owns wireless communication and is connected to the STM32 over SPI.

Required:

* Proper module power and decoupling.
* SPI signals.
* DATA_READY input.
* SWD programming/debugging.
* Reset/recovery access.
* Appropriate module GPIO selection.
* Antenna keepout and RF placement requirements.

Do not assign SPI or other high-speed signals to module pins restricted by Raytac’s layout/RF guidance. Do not invent module pad numbers from generic nRF52840 silicon pin numbers.

## 7. STM32 ↔ nRF communication — selected architecture

Use **4-wire SPI plus DATA_READY**.

Preferred roles:

* nRF52840 = SPI master.
* STM32 = SPI slave.

Signals:

```text
SPI_SCK
SPI_MOSI
SPI_MISO
SPI_CS_N
STM_DATA_READY
GND
```

The nRF owns RF scheduling and can request the latest processed key snapshot shortly before transmission.

The STM32 continuously scans/processes keys and maintains a coherent latest-state buffer. The nRF reads that snapshot over SPI.

Initial development SPI speed can be conservative, e.g. 8 MHz. Do not assume 32 MHz operation is required.

The protocol is not yet frozen. It should include a deterministic way to identify fresh/coherent data, such as sequence numbers and a defined transaction format. CRC, status, command handling, and reset synchronization should be designed deliberately rather than invented during schematic generation.

Do not assume DATA_READY alone guarantees a fresh packet or that a key event will be delivered before every RF deadline. The firmware protocol must handle asynchronous MCU timing.

A possible additional nRF → STM32 reset/control line was discussed but not finalized.

## 8. Programming and debugging

The user wants simple **right-angle headers that can remain installed**.

Each MCU should have independent SWD access.

STM32:

* VTREF / 3.3 V reference.
* GND.
* SWDIO.
* SWCLK.
* NRST.

nRF52840:

* VTREF / 3.3 V reference.
* GND.
* SWDIO.
* SWCLK.
* nRESET if supported/configured on the selected module.

A 1×5 right-angle 2.54 mm header was proposed, but exact connector/pin order should be finalized and labeled clearly.

The target board powers itself; debugger VTREF is a voltage reference, not an invitation to back-power the keyboard.

STM32 development: ST-Link / STM32CubeIDE or equivalent SWD tooling.

nRF development: nRF Connect SDK, VS Code, J-Link-compatible debugging, SEGGER RTT logging. An nRF52840 DK can potentially serve as an external debugger, subject to its documented external-target wiring.

Both MCUs should be independently debuggable while the board is operating. Include accessible SPI test points for a logic analyzer.

## 10. Sleep and wake — important unresolved issue

The Hall sensors can be disabled to reduce idle power, but fully disabled sensors cannot detect a key press.

A real wake strategy is required, such as periodic low-rate scanning or another deliberate mechanism.

Do not implement “turn all Hall sensors off, then wake immediately on key press” without explaining how the key press is detected.

Active scan performance and idle battery life are separate operating modes. Battery runtime must be calculated from actual measured or datasheet-supported current budgets, not guessed.

3. Hall sensing — what is actually validated

We originally considered the DRV5056, but moved away from it because its active current is poorly suited to our battery-powered design. TI’s TMAG5253 is a substantially better fit: it supports 1.65–3.6 V operation, has a dedicated enable pin, a high-impedance output in shutdown, and a BA3 bipolar range of ±80 mT. TI also publishes a keyboard-specific application note. These are actual documented capabilities, not assumptions.

We discussed a 2×9 multiplexed architecture, then deliberately rejected it for the performance version. Our decision is:

18× TMAG5253
    │
    ├── 18 independent analog signals
    └── common HALL_EN
             ↓
       STM32 ADC1 / ADC2
             ↓
       DMA + key processing

All sensors remain awake during active use, avoiding repeated enable/wake delays. The tradeoff is higher active Hall current and more ADC pins. This does not make detection literally instantaneous—latency still includes sensor response, ADC sampling, processing, SPI, RF scheduling, and host handling.

One correction to my earlier explanation: shutting all Hall sensors down means they cannot detect a keypress while off. We will need periodic wake-and-scan or another explicit wake mechanism. We have not designed that yet.

5. STM32 ↔ nRF communication — frozen architecture

We agreed on SPI, with the nRF as master and STM32 as slave.

STM32                         nRF52840
------                        --------
SPI_MISO ------------------> SPI_MISO
SPI_MOSI <------------------ SPI_MOSI
SPI_SCK  <------------------ SPI_SCK
SPI_CS_N <------------------ SPI_CS_N

DATA_READY ----------------> GPIO interrupt

The STM32 maintains the latest processed key-state snapshot. The nRF requests it when needed for wireless transmission. We discussed compact packets containing a sequence number, key bitmap, status, and CRC, but the packet format is not frozen.

We have also not decided whether to add a dedicated nRF→STM32 reset/control line or a hardware timing/synchronization line. Those are still design decisions, not existing schematic connections.

6. Programming and debugging — frozen requirements

Both MCUs get independent SWD access using right-angle headers that can remain installed.

For the STM32, we need SWDIO, SWCLK, NRST, GND, and target-voltage reference. For the nRF52840, we need the equivalent SWD signals and reset access. The exact connector pin order and module-pad assignments still need to be drawn.

The nRF52840 DK has an onboard SEGGER J-Link and officially supports programming/debugging external targets through its debug-out connector. We can use that rather than buying an expensive standalone debugger. Nordic recommends externally powering the target and ensuring compatible debug voltages.

Our development setup can therefore be:

ST-Link → STM32 SWD

nRF52840 DK / J-Link → nRF SWD

Logic analyzer → SPI + DATA_READY
7. What has not been validated yet

The most important distinction is that we have validated component capabilities and architectural precedent, not a complete working Kaboard circuit. We have not built a prototype, measured Hall output with our actual switch, completed the MCU pin assignments, or run a full schematic ERC.

The remaining critical items are the exact STM32 pin map, exact Raytac module selection and pin map, Hall sensitivity/physical placement, full power schematic audit, battery pack/NTC/connector verification, sleep/wake behavior, buttons/LEDs, and the actual receiver/RF implementation.

The STM32G431 family does have two fast 12-bit ADCs and substantial peripheral capability, but that does not prove that 18 external ADC inputs, SPI, SWD, battery measurement, and all control pins fit simultaneously on our chosen LQFP64 package. That is precisely the pin-level audit we still need to perform.

Bottom line: the system architecture is now quite stable. The next task should be only the STM32G431RBT6 full pin map, with every ADC, SPI, SWD, power, and control pin checked against the exact package datasheet. We should not move on to the nRF map or Codex schematic until that is complete.
